## 修复：发消息响应慢 + 无法发送

定位到消息发送链路三处根因并修复：

1. **模型流式调用缺首字节超时**（`src/host/model-facade.ts`）
   - 原实现只有总超时 `setTimeout(abort, timeoutMs)`（60s），reasoning 模型（deepseek-v4.1-flash，走阿里云 MaaS）首字慢或流中断时需等满 60s。
   - 新增 `firstByteTimer`（`min(timeoutMs, 20000)`），首个 chunk 到达即清除；仅在无数据流时快速超时。

2. **QQ 发送队列满时静默丢消息 + 串行链卡死**（`src/host/qq-gateway.ts`）
   - `enqueueTurn` 里 `#queuedTurns>=4` 原直接 `statusSafe('queue-full')` 静默丢弃，改为回一条临时提示让发送方重试。
   - `runTurn` 新增 90s 整体超时（`AbortSignal.timeout(90000)`），避免单条消息卡住整个 `#serial` 串行链。

构建已通过（`runtime/node/node.exe ... npm run build`，tsc 编译成功）。

## 修复：聊天"太慢"（推理模型 reasoning_effort 未生效）

用户要求只能用 `deepseek-v4.1-flash`（不能换非推理的 4.0）。根因是 **`model-facade.ts` 的正则 bug**：

- 原判断 `lowEffort` 的正则 `/(?:^|\.)maas\.aliyuncs\.com$/i` 要求 hostname 以 `.maas.aliyuncs.com` 结尾，但实际 baseURL hostname 是 `llm-...cn-beijing.maas.aliyuncs.com`（多了 `cn-beijing.` 前缀），恒不匹配 → `reasoning_effort:'low'` 从未传出 → deepseek-v4.1-flash 用了默认 `high` 推理强度（思考约 59 token，思考"永远开启"）。
- 修复：正则改为 `/(?:^|\.)aliyuncs\.com$/i`，`low` 档真正生效（思考约 10 token，首字大幅提速）。
- 另补齐 `chat-service.ts` 的 `extractLabor` 漏掉的 `reasoningEffort:'low'`。

关键背景（来自阿里云百炼文档）：deepseek-v4.1-flash 默认 `reasoning_effort=high`，支持 `low`/`high`/`max`，**不支持 none/关闭思考**；思考 token 通过 `reasoning_content` 输出（代码忽略它，只消费 `content`，正确）。

## 修复：聊天"一秒内回复"（实测驱动）

用户要求输入框发消息 1 秒内回复。实测（阿里云百炼 deepseek-v4.1-flash-1017）发现：

- `reasoning_effort:'low'` 单独传：首字 ~773ms、思考 105 token（**思考仍开启**）。
- **`reasoning_effort:'low'` + `enable_thinking:false`：首字 ~367ms、思考 0 token**（阿里云百炼支持 `enable_thinking:false` 真正关闭思考，这是 DeepSeek 官方 API 不支持的，之前搜到的"无法关闭"结论不适用于阿里云百炼）。

三项改动：
1. **`model-facade.ts`**：对阿里云百炼的 deepseek-v4.1-flash，`lowEffort` 时同时传 `reasoning_effort:'low'` 和 `enable_thinking:false`（首字 1.4s → ~0.4s）。
2. **`semantic-grounding.ts`**：加"纯闲聊快速路径"——回复不含事实/动作/时间声明（正则 CLAIM）时跳过 2 次模型核查，直接返回全 other 片段 review（~0ms）。搬砖/工作/身体状态/时间性声称仍走完整核查，安全不受影响。
3. 正则 `maas.aliyuncs.com` → `aliyuncs.com`（修复 reasoning_effort 未生效的 bug，见上条）。

实测优化后普通闲聊：生成首字 ~360-680ms，核查 ~0ms（快速路径），总延迟 <1s。

## 修复：看不到"扣没扣饭钱"（买饭扣款不留痕）

用户反馈看不到饭钱（token）被扣。定位到扣款有两处、但显示只覆盖一处：

- 扣款路径① 喂饭 `care.feed` → `settleSimulatedSpending(draft,'feed')` 会 push `pet.events` 里的 `wallet-spend` 事件，能被"近期饭钱与工钱操作"列表看到（`finance-management.ts` 的 read 只筛选 `wallet`/`wallet-spend`/`labor` 三种 kind）。
- 扣款路径② 买饭 `service.buy-rice`（`outcome-projector.ts`）→ 直接 `wallet.balance -= charge`，**不 push 任何 event**。而"她饿了自动买饭"（`deterministic-life.ts` `/冰箱 买一碗白饭`）正是主要自动扣款场景，扣了钱界面完全无记录，用户自然看不到。

修复：`outcome-projector.ts` 的 `service.buy-rice` 分支，`charge>0` 时 push `wallet-spend` 事件到 `pet.events`（文案 `买饭消耗 X token，余额 Y token`）并同步写入 `draft.life.events`（type `wallet.spend`），与喂饭路径保持一致。构建已通过。

注意：探索 `learning.observe`/`image.observe` 的扣款在 `action-coordinator.ts` 的 queue 阶段"预扣"并存入 `explorationCharges`，同样未 push wallet-spend 事件，且失败回退逻辑复杂，本次未改动（避免引入新 bug），后续如需可见可单独处理。

## 补充修复：手动减少饭钱"桌宠不知道"

用户反馈手动减少余额后"它（桌宠）应该知道"。排查结论：

- 手动 add/subtract/set/freeze 在 `vendor/pet-plugins/behavior/core.mjs` 的 `wallet()` 里会 `eventIn(p,'wallet',...)` 写入 `p.events`（kind=`wallet`，text「爸把饭钱从 X 改为 Y token」），并经 `legacy-domain.ts` 同步到 `life.events`（type=`wallet`/`wallet-spend`）。**数据与界面"近期饭钱与工钱操作"都能看到这条记录，数据层没问题。**
- 但这条 `wallet` 事件只进 `life.events`，**没生成 memory**（`memory-retrieval.ts` 的 `search` 只检索 `life.memories`），且 `conversation-context.ts` 的 `food` 只含 balance/frozen/price/inventory/eating，**没有"最近饭钱变动"**。所以桌宠聊天时只知道"当前余额数字"，不知道"爸爸刚手动扣了钱"这个动作。

修复：`conversation-context.ts` 的 `food` 增加 `recentChanges` 字段——从 `pet.events` 取最近 6 条 `wallet`/`wallet-spend` 事件的 `text`（字符串数组，含手动调整和自然消耗文案），随 `situation` 注入 system prompt，桌宠据此知道最近的饭钱变动。构建通过。

（本轮另外：`outcome-projector.ts` 的买饭扣款已补 `wallet-spend` 事件，见上一条。）

## 把"扣钱"记进长期记忆（wallet 事件 → memory）

用户要求把手动调整饭钱（扣钱/加钱/设余额/冻结）当作一件事记进长期记忆。实现：

- `legacy-domain.ts` 的 `mutate` 通用事件同步循环里，当 `event.kind==='wallet'`（手动调整，区别于 `wallet-spend` 自然消耗）时，额外生成一条 `autobiographical` memory 写入 `draft.life.memories`。
- memory 内容用 `event.text`（「爸把饭钱从 X 改为 Y token」/「爸冻结了饭钱消耗」等），`sourceIds` 绑定对应的 `life.event` id（`namespaced('event', event.id)`），`evidenceLevel:'observed'`，来源约束与失效逻辑通用。
- 这样桌宠聊天检索（`memory-retrieval.ts` 检索 `life.memories`）时能搜到"爸爸扣了钱"这件事，成长页"记忆"里也显示为"个人历程"。

遗留：目前手动扣钱表单（`finance.js` 的 wallet-form）无"原因"输入，记忆只记录"扣了多少"、不含"为什么扣"。若需要让桌宠记住"扣钱的原因"（如她做错了什么），需在 UI 增加原因输入并透传到 wallet 操作 + memory 内容，属后续增强。

## 修复：聊天报「对话未完成，请检查状态后重试」

用户要求彻底消除该错误。根因链：

1. 桌面聊天 `turn()` 走语义审核（`semantic-grounding`）。`reviewedReply` 原来对**任意** `supported:false` 片段都返回 null（`segments.some(s=>!s.supported)`），而审核器把"嗓子干""想喝水"等主观感受误判为 `fact` 且无证据 → 整句被拒 → 抛 `RETRY_NATURAL_REPLY` 重试。
2. 审核 `valid()` 要求 `actionFactsSignature` 精确匹配，但审核与提交之间桌宠状态（身体数值/回执时间戳）会因自主唤醒而变 → signature 抖动 → 反复失配。
3. 重试 3 次耗尽 → `!committed` → 抛「对话未能在当前状态下核实」→ HTTP 层 `catch{}` 兜底吞成笼统的「对话未完成，请检查状态后重试」。

三处修复（`chat-service.ts` + `semantic-grounding.ts`）：
1. **`reviewedReply` 放宽**：只有 `fact`/`intent` 片段要求 supported，`other`（情绪/愿望/提问）始终放行，避免正常闲聊被误伤。
2. **兜底降级**：重试耗尽时不再抛错，改用最后一份已脱敏、长度合法的 `lastOutput` 直接提交（workIntent 不触发，因未经审核），确保对话必能返回。
3. **HTTP 层暴露真实错误**：`catch{...}` 改为 `catch(error){...error.message...}`，不再吞掉具体原因（如"模拟饭钱已用完，请先添加饭钱"）。

构建通过。彻底消除「对话未完成」这一笼统兜底提示。

## 功能：搬砖工地「强行开干」按钮（非硬编码学习闭环）

需求：工地加"强行开干"按钮，无视身体状况强制搬砖、指标可扣成负；桌宠被强制后产生记忆，之后通过经验学习避免再被按下（不硬编码规则）。

实现（4 层，全部非硬编码）：

1. **后端 force-work 动作**（`worksite.ts`）：新增 `force-work` action，要求有 `working`/`paused` 且未完成的约定，设 `contract.status='working'`、`contract.forced=true`、`workPermit=true`、`batchRemaining=1`，中断当前 command 并 `wake` 触发搬砖。
2. **强制决策短路**（`deterministic-life.ts`）：`contract.forced` 时跳过 `tired`/`weak`/`overdue` 判断，`choice='work'`；`nextDecision` 到期也不因休息而停止。身体门槛由决策层（forced）控制，不再硬编码。
3. **身体透支**（`outcome-projector.ts` + `body-projection.ts` + `legacy-import.ts`/`main.ts`）：`contract.forced` 时体力/精力扣减不设下限（`Math.max(-100, ...)`）可到负，pain/stress 额外累积（真实"难受"）；`labor.step` 能力的 bodyLimits 放宽为 `allowSleeping/allowRestrained/allowInjured:true,minStamina:-101,maxPain:101`（物理层不拦，决策层把关），`projectBody` 对 stamina/energy/satiety 放宽到 [-100,100] 允许负值。
4. **记忆 + 非硬编码学习**：force-work 产生 `interaction.worksite` 事件（action=`force-work`）→ 生成 autobiographical 记忆（内容为事实「爸爸强行按下要我继续搬砖」，不硬编码情绪）；`worksite-reactions.ts`/`legacy-responses.ts` 扩展支持 force-work，让桌宠基于真实透支的 `stats/emotions/desires` 自然回应（模型生成，不写死"难受"）。透支→pain 升高→进入 `cognition` 的 Appraise（pain>=50）和 `strategyScore`，她自然在后续自主决策中避免身体崩溃（即减少被强制的机会）——这是经验学习，非硬编码。

UI（`vendor/dsh-pet/runtime/electron-helper/worksite.html/js/css`）：header 加红色"强行开干"按钮，有进行中/暂停约定且她在工地时显示，点击调 `worksite.action('force-work')`。

构建通过。注意：worksite.html/js/css 在 vendor 目录，不走 tsc，需随部署同步。
